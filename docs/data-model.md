# Proposed Prisma data model

Design only: no `schema.prisma`, generated client, migrations or database have been created. This catalog defines intended Prisma types, relations, uniqueness and SQL constraints. Translate it into a complete validated schema in M1, adding later models only when their milestone needs them. PostgreSQL is required for the locking and constraint tests.

## Conventions

- Application IDs: `String @id @default(uuid()) @db.Uuid`. Provider IDs are opaque `String` values, never UUID-coerced or taken as proof of ownership.
- Common timestamps: `createdAt DateTime @default(now()) @db.Timestamptz(3)`; mutable records add `updatedAt DateTime @updatedAt @db.Timestamptz(3)`. Approval, consent, quotes and audit are immutable facts, not overwritten histories.
- `Minor` money fields: `BigInt @db.BigInt`; `currency String @db.Char(3)`. No Prisma `Float` for money. Amount-bearing API DTOs encode minor units as decimal strings. JSON snapshots likewise encode any money as decimal strings.
- `?` below means nullable; enum names identify application enums to implement, not provider enums. Store raw provider status separately and allow unknown provider values to fail closed.
- Every tenant-owned row has `merchantId String @db.Uuid`, a relation to Merchant and `@@unique([merchantId, id])`. Child relations use composite foreign keys including tenant ID. Reverse list relations must be included in the implementation. Use restrictive deletes for financial/history records; no cascading deletion of payments, consent or audit.
- Every mutable business aggregate has `version Int @default(0)` for stale-client/concurrency checks. DB locks/CAS, not UI disabled buttons, enforce correctness.

Prisma supports [multi-field relations](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/relations/one-to-many-relations); the implementation must validate its exact chosen version. The following is relation notation for the design, not a complete executable schema:

```text
Payment (merchantId, orderId) -> Order (merchantId, id)
ReturnCase (merchantId, orderId) -> Order (merchantId, id)
ReturnQuote (merchantId, caseId, orderId) -> ReturnCase (merchantId, id, orderId)
ResolutionDecision (merchantId, chosenQuoteId, caseId, orderId)
  -> ReturnQuote (merchantId, id, caseId, orderId)
RefundOperation (merchantId, decisionId, orderId)
  -> ResolutionDecision (merchantId, id, orderId)
RefundOperation (merchantId, paymentId, orderId)
  -> Payment (merchantId, id, orderId)
```

Add corresponding composite unique keys on referenced parents. This prevents linking a decision to a quote from another case or linking its refund to another order, even within the same tenant.

An unexpired token or an AI low-uncertainty response alone cannot make an offer eligible. Approval rechecks the current policy, assessment, evidence/case version, fulfillment conditions and quote. Document approved policy changes as new facts; old approvals are not silently migrated.

| `WebhookEvent` | `id String @id` (PayPal event ID), `merchantId String?`, `eventType String`, `resourceId String?`, `resourceType String?`, `providerCreatedAt DateTime?`, `verifiedAt DateTime`, `receivedAt DateTime`, `processedAt DateTime?`, `processingStatus WebhookStatus`, `redactedResourceJson Json`, `payloadHash String`, `attemptCount Int`, `nextCheckAt DateTime?`, `lastErrorCode String?` | Insert only after successful signature verification; event ID is global dedupe key. Minimize stored data but retain identifiers/amounts/link relationships needed for reconciliation. |
| `AuditLog` | `merchantId`, `actorType ActorType`, `actorUserId String?`, `caseId String?`, `paymentId String?`, `refundOperationId String?`, `action String`, `correlationId String`, `redactedMetadataJson Json`, `createdAt DateTime` | Composite FKs where applicable, including optional actor User; index merchant/case/createdAt and merchant/createdAt. INSERT-only runtime grants/trigger protection; migrations use a separate owner role. No credentials, bearer tokens, raw evidence or full provider responses. No updatedAt. |

`OperationStatus`: `PENDING`, `PROCESSING`, `PROVIDER_PENDING`, `NEEDS_RECONCILIATION`, `COMPLETED`, `FAILED_FINAL`. `ReservationState`: `HELD`, `SETTLED`, `RELEASED`. An uncertain/retryable error is not final. Release only after verified non-execution/final failure; lease expiry is not proof of failure.

`CaseStatus`: `MANUAL_REVIEW`, `PENDING`, `AWAITING_CUSTOMER`, `AWAITING_RETURN`, `APPROVED`, `PROCESSING`, `COMPLETED`, `FAILED`. Status transitions are service-enforced and audited; case completion depends on verified payment completion, not quote acceptance.

## Constraints beyond the Prisma schema

Implement via reviewed SQL migrations plus service tests. Prisma field declarations alone cannot enforce aggregate or conditional business invariants.

1. SQL checks: uppercase supported currency, positive captured/refunded/approved amounts, nonnegative component estimates, valid lengths and integer bounds. Modeled total cost is allowed to be signed. Token purpose/target combinations must be valid.
2. Composite foreign keys described above, plus same-case quote/assessment and same-quote acceptance/decision constraints. Add the referenced unique tuples in generated schema/migrations and verify them against real PostgreSQL.
3. Partial unique index for active cases per merchant/order. A second concurrent approval is also stopped by `ResolutionDecision.caseId` uniqueness, not just by one `RefundOperation` per decision.
4. Lock Payment while computing capacity, inserting/reserving an operation, or settling its verified refund. Compute completed debits from unique ProviderRefund rows; add held reservations; add external provider-pending amounts without a matching operation. Never count the same application's pending refund both as ledger pending and reservation.
5. Settle ledger insertion, operation reservation transition, case/decision status and audit in one transaction. Recheck raw provider state and operation ownership before settlement. A mismatch freezes the payment and preserves evidence for review.
6. Immutable decision/quote payloads and insert-only audit/consent protection. Exact retries cannot mutate amount/currency/capture/request hash. SQL/runtime grants and application tests enforce this; don't claim append-only history if the runtime role can rewrite it freely.
7. Provider calls occur outside DB transactions. Use short row-locking transactions or serializable transactions with bounded contention retry. Retrying a DB transaction never resends a payment call. See [Prisma v7 transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions).

There is deliberately no cached `remainingRefundableMinor` column treated as truth. A view/service derives it from verified capture, ledger and reservations. Foreign key checks cannot prove external ownership; the PayPal adapter verifies it. Tests must cover both layers.
